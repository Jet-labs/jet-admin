Local Setup

This page takes you from a clone to a working local installation. Commands are verified against package.json, docker-compose-sample.yml, Dockerfile.*, docker-entrypoint.*.sh, apps/backend/environment.js, and the frontend runtime config.

PathBest forWhat runs
A — DockerFirst evaluation, demos, reference stackFrontend, backend, PostgreSQL, Redis, listener proxy, Temporal, optional RustFS and MCP
B — NativeDay-to-day development with hot reloadVite frontend, nodemon backend, package watchers, Docker infrastructure
Just want to build something?

The Quickstart walks through a complete application after the stack is running. Use this page to get the stack healthy first.

1. Prerequisites​

RequirementVersion / detailWhy it matters
Node.js20.x (root engines)Backend, frontend build, MCP, workspace packages.
npmShips with Node 20; workspacesnpm install at the root installs apps/* and packages/*.
PostgreSQL14+; reference compose uses postgres:15-alpineSystem store for tenants, assets, IAM, audit, application metadata.
Docker + ComposeRecent Docker Desktop / Engine with Compose v2Recommended path and easiest way to get Redis/Temporal.
Firebase projectWeb app config + service-account JSONHuman sign-in. The frontend has no fallback; the backend verifies ID tokens.
S3-compatible storage (optional)Endpoint, keys, bucketFile uploads. The app runs without it, but uploads fail.
OpenRouter key (optional)OPENROUTER_API_KEY or tenant vault ai_configJet Agent. Everything else works without it.
Temporal (optional)Bundled in Docker, or standaloneDurable workflow driver. The native driver works without Temporal.
RedisRequired for listeners and Socket.IO fan-outThe listener pipeline is proxy-only and publishes to Redis Streams.
Firebase is not optional for human login

There is no local username/password fallback. If the seven VITE_FIREBASE_* values are missing, initializeApp throws and the app is blank. API keys do not replace Firebase for interactive users.

3. Path A — Docker quick start​

Step 1: Create the environment file​

cp .env.docker .env

PowerShell: Copy-Item .env.docker .env. docker compose reads .env automatically. Do not commit it.

Step 2: Set the minimum values​

VariableWhat to use
POSTGRES_PASSWORDStrong password; must match an existing volume if reusing one.
VAULT_ENCRYPTION_KEY32-byte hex, e.g. openssl rand -hex 32. Changing it later makes stored credentials unreadable.
OAUTH_STATE_SECRETRandom secret for OAuth state tokens. Set it even if Google sign-in is optional.
FIREBASE_CREDENTIALSFirebase service-account JSON as one line, wrapped in single quotes.
SEED_DATABASEtrue for the first boot, then false.
VITE_SERVER_HOST / VITE_SOCKET_HOSThttp://localhost:8090 for the default local stack.
POSTGRES_USER / POSTGRES_DBpostgres / jet_admin_db unless intentionally changed.
The seed flag is easy to miss

.env.docker ships with SEED_DATABASE=false. The sample compose defaults the same variable to true, but the value in .env wins. Copying .env.docker unchanged and starting on a fresh volume leaves the schema empty; login and queries then fail with missing-table errors. Set SEED_DATABASE=true before the first up.

Step 3: Put Firebase web config into the frontend build​

The sample compose hardcodes placeholder VITE_FIREBASE_* build arguments. The VITE_FIREBASE_* values in .env.docker are not automatically passed into them. Replace the placeholders in the compose file (or a local copy/override) before building. The frontend also accepts runtime SERVER_HOST / SOCKET_HOST, written to /config.js by docker-entrypoint.frontend.sh, but Firebase values are baked at build time.

Step 4: Start the stack​

docker compose -f docker-compose-sample.yml up -d --build

Equivalent: npm run docker:up. If your Docker host is remote, change VITE_SERVER_HOST, VITE_SOCKET_HOST, and CORS_WHITELIST to browser-reachable URLs. localhost inside a container is the container, not your machine.

Step 5: Understand the first boot​

docker-entrypoint.backend.sh:

  1. Waits up to 60 seconds for PostgreSQL with pg_isready.
  2. If SEED_DATABASE=true: runs npx prisma db push, then node scripts/run-manual-migrations.js for prisma/migrations/manual/*.sql, then npm run seed to create permissions, built-in roles, and the system user.
  3. Starts Node behind nginx.

The seed does not create a demo tenant, datasource, or app page.

Why not prisma migrate deploy?

The repo keeps SQL history in prisma/migrations/manual/ and deliberately uses prisma db push in the entrypoint. migrate deploy aborts with P3015 because there is no standard Prisma migration directory. Use db push + the manual runner.

Step 6: Optional profiles​

# Bundled S3-compatible storage (RustFS)
docker compose -f docker-compose-sample.yml --profile storage up -d rustfs storage-init

# MCP server for external AI clients
docker compose -f docker-compose-sample.yml --profile mcp up -d mcp-server

# Temporal CLI tools
docker compose -f docker-compose-sample.yml --profile tools up -d temporal-admin-tools

mcp-server requires FIREBASE_CREDENTIALS; it exits without it. RustFS defaults to rustfsadmin / rustfsadmin; change those before exposing the ports. Temporal is the only workflow engine: starting the Temporal profile is required for workflow execution. Set TEMPORAL_ADDRESS, TEMPORAL_NAMESPACE, and TEMPORAL_TASK_QUEUE to match the worker. The legacy WORKFLOW_ENGINE_DRIVER variable is still read but has no effect.

Step 7: Verify​

docker compose -f docker-compose-sample.yml ps
curl http://localhost:8090/health
curl http://localhost/health

Expected: services running/healthy; the API returns {"status":"ok","timestamp":"..."}; nginx returns OK; Temporal UI loads at http://localhost:8088.

docker compose -f docker-compose-sample.yml logs -f backend
docker compose -f docker-compose-sample.yml logs -f listener-proxy

Application logs are in the jet-admin-backend-logs volume and /app/apps/backend/logs/. docker compose logs backend shows entrypoint/Node output, not every application log line.

4. Path B — Native development​

Step 1: Install dependencies and build packages​

npm install
npm run build:packages

build:packages is required on a fresh clone because workspace packages resolve to dist/index.cjs / dist/index.mjs, and dist/ is gitignored. Docker images build packages themselves; a native checkout must do it explicitly.

Step 2: Start infrastructure​

docker compose -f docker-compose-sample.yml up -d postgres redis
npm run temporal:up   # optional

Do not run the standalone Temporal compose and the full sample compose at the same time: both use jet-admin-network and host ports 7233, 8088, 5433. If 5432 is taken, set POSTGRES_HOST_PORT (e.g. 5433) and update DATABASE_URL.

Step 3: Create apps/backend/.env​

There is no tracked apps/backend/.env.example in this checkout. Create the file yourself; use root .env.docker as a reference, but change container hostnames to localhost.

NODE_ENV=development
PORT=8090
DATABASE_URL=postgresql://postgres:YOUR_POSTGRES_PASSWORD@localhost:5432/jet_admin_db
REDIS_URL=redis://localhost:6379
VAULT_ENCRYPTION_KEY=YOUR_64_HEX_CHARS
OAUTH_STATE_SECRET=YOUR_RANDOM_SECRET
FIREBASE_CREDENTIALS='{"type":"service_account",...}'
ENABLED_MODULES=auth,tenant,database,datasource,dataQuery,workflow,widget,dashboard,userManagement,role,apiKey,cronJob,audit,ai,notification,permission
CORS_WHITELIST=http://localhost:5173,http://127.0.0.1:5173
LISTENER_PROXY_PORT=8095
TEMPORAL_ADDRESS=localhost:7233
TEMPORAL_NAMESPACE=default
TEMPORAL_TASK_QUEUE=jet-admin-workflows
# Optional: S3_* for uploads, OPENROUTER_API_KEY for Jet Agent
ENABLED_MODULES defaults are minimal

If omitted, environment.js enables only auth and tenant. The UI loads, but datasource, query, workflow, widget, and page routes are missing or fail. Use the full list above for a normal development instance.

Step 4: Bootstrap the database​

cd apps/backend
npx prisma db push
node scripts/run-manual-migrations.js
npm run seed
cd ../..

npm run seed creates the permission catalogue, built-in roles, and a system user; it does not create demo business data. Check migration status with node scripts/run-manual-migrations.js --status.

Step 5: Create apps/frontend/.env​

VITE_SERVER_HOST=http://localhost:8090
VITE_SOCKET_HOST=http://localhost:8090
VITE_FIREBASE_API_KEY=...
VITE_FIREBASE_AUTH_DOMAIN=your-project.firebaseapp.com
VITE_FIREBASE_PROJECT_ID=your-project
VITE_FIREBASE_STORAGE_BUCKET=your-project.firebasestorage.app
VITE_FIREBASE_MESSAGING_SENDER_ID=...
VITE_FIREBASE_APP_ID=...
VITE_FIREBASE_MEASUREMENT_ID=...
VITE_WEBHOOK_PORT=8095

All seven Firebase values are required by src/config/firebase.js.

Step 6: Run the applications​

npm run dev:all

This runs temporal:up and concurrently starts Vite (:5173), backend nodemon (:8090), and the dev:* package watchers (except dev:ui). The root start:b script uses the Windows set NODE_ENV=development&& … form. On macOS/Linux, use cd apps/backend && npm run dev so the POSIX export form sets the environment explicitly.

CommandWhat it starts
npm run start:fVite frontend
npm run start:bBackend nodemon (Windows form)
cd apps/backend && npm run devBackend nodemon (POSIX form)
npm run dev:all-packagesPackage watchers
npm run dev:uiShared UI watcher (not in dev:all-packages)
npm run start:mcpMCP HTTP server on :5001
npm run start:listener-proxyListener proxy on :8095
cd apps/backend && npm run temporal:workerTemporal workflow worker
npm run temporal:*Temporal lifecycle

Step 7: Run listeners locally​

The backend no longer subscribes to datasources itself. Listener runtime needs PostgreSQL + Redis + listener-proxy + backend.

docker compose -f docker-compose-sample.yml up -d redis
# create apps/listener-proxy/.env from .env.example; match DATABASE_URL,
# REDIS_URL, and VAULT_ENCRYPTION_KEY with the backend
npm run start:listener-proxy

VITE_WEBHOOK_PORT only changes the displayed test URL; ingestion goes through the proxy on :8095.

Step 8: Run the docs site​

cd docs
npm ci
npm start

Production build: npm run build.

Optional: one-command launcher​

start.ps1 / start.sh wrap scripts/start.js:

.\start.ps1                 # core: frontend + backend + infrastructure
.\start.ps1 --all           # all apps + storage + tools profiles
.\start.ps1 --all --mode dev
.\start.ps1 --stop
.\start.ps1 --list

The launcher expects a local docker-compose.yml, which is gitignored. Copy docker-compose-sample.yml to docker-compose.yml and edit it first if you want the launcher to use your configuration. The explicit commands above are what this page verifies.

First useful smoke test

Create a tenant, add a PostgreSQL datasource pointing at a non-production database, create a SELECT 1 AS ok query, test it, and bind it to a Text or Table widget. That exercises auth, tenant scoping, credential decryption, the connector, the query engine, and the page runtime in one pass.

6. Migrations and schema changes​

Jet Admin uses a two-part schema workflow:

PartToolPurpose
Prisma schemanpx prisma db pushReconciles tables/columns/relations from schema.prisma.
Manual SQLnode scripts/run-manual-migrations.jsConstraints, indexes, backfills, features in prisma/migrations/manual/*.sql.
Seednpm run seedPermission catalogue, built-in roles, system user.

Applied manual files are recorded in _manual_migrations, so the runner is safe to re-run; it applies files in filename order and reports per-file failures.

cd apps/backend
npx prisma db push
node scripts/run-manual-migrations.js
npm run seed

For production-like changes: review the db push plan, back up the database, apply manual SQL deliberately, and restart the backend. Do not rely on db push to preserve data through destructive changes.

No generic migration framework

prisma migrate dev is not the bootstrap path, and prisma migrate deploy fails with P3015 because there is no standard Prisma migration history. If you introduce a formal process, document it and update the Docker entrypoint.

GoalCommandEffect
Stop, keep datadocker compose -f docker-compose-sample.yml downContainers stop; named volumes remain.
Full Docker resetdocker compose -f docker-compose-sample.yml down -v --remove-orphansDeletes app DB, Redis, Temporal, logs, and RustFS data.
Remove local images toodocker compose -f docker-compose-sample.yml down -v --rmi localAlso deletes locally built images.
Reset only app DBdown, docker volume rm jet-admin-postgres-data, then up -d --buildNew empty app database; set SEED_DATABASE=true.
Reset only Temporalnpm run temporal:cleanRemoves Temporal volume only.
Native DB resetnpx prisma db push --force-reset + manual runner + seedDrops/recreates the schema; destructive.
Delete one tenantUI, or DELETE /api/v1/tenants/:tenantIDCascades tenant resources and policies; irreversible.

Named volumes: jet-admin-postgres-data, jet-admin-redis-data, jet-admin-backend-logs, jet-temporal-postgres-data, jet-rustfs-data.

Clean up a quickstart demo​

  1. Archive the application in Application Studio (releases and page links are retained; there is no release delete route).

  2. Delete the demo tenant to remove its pages, widgets, queries, datasources, and roles in one operation.

  3. Drop the separate demo database:

    docker exec -it jet-admin-postgres psql -U postgres -c "DROP DATABASE IF EXISTS jet_demo;"
