# Datasources

Datasources are Jet Admin's connection layer to systems outside the platform. They define how the application authenticates with and communicates with databases, APIs, SaaS products, messaging systems, and other external services.

## What a datasource is

A datasource record usually captures:

- the datasource type,
- connection credentials or connection metadata,
- connector-specific configuration,
- the execution contract used by higher-level features such as queries, widgets, and workflows.

## Supported platform shape

The current monorepo implements datasource functionality across multiple packages:

- `@jet-admin/datasource-types` for canonical datasource metadata,
- `@jet-admin/datasources-logic` for backend connector logic,
- `@jet-admin/datasources-ui` for frontend configuration forms.

This package split is important because Jet Admin does not treat datasource support as a single hard-coded screen. It is an extensible subsystem.

## Datasource categories in the current codebase

The repository includes support or definitions for a broad set of datasource types, including examples such as:

### Relational and analytical data stores

- PostgreSQL

### NoSQL and document/graph stores

The exact operational maturity of each connector can differ, but the current codebase is clearly structured around a large datasource catalog.

## Current backend capabilities

The datasource API currently supports:

- list datasources,
- create datasource,
- get a datasource,
- update datasource,
- clone datasource,
- delete datasource,
- test datasource connectivity.

These operations are tenant-scoped and are consumed by the frontend management screens.

## Why datasources matter

Datasources are upstream dependencies for several other Jet Admin features:

- **queries** execute against datasource connections,
- **widgets** often visualize datasource-backed results,
- **workflows** can trigger datasource-backed operations,
- **dashboards** surface the results of those higher-level features.

## Datasource lifecycle

A typical datasource workflow looks like this:

1. create a datasource,
2. choose the connector type,
3. fill in connector-specific settings,
4. test the connection,
5. save it for reuse by queries, widgets, and workflows,
6. clone it when a similar environment/configuration is needed.

## Security and ownership

Datasource configuration is tenant-scoped application metadata. The platform stores the configuration needed to connect, but the underlying external system remains tenant-managed or third-party managed.

That separation is important when reasoning about platform data flow:

- Jet Admin owns the datasource definition record,
- the tenant or third party owns the external data system itself.
