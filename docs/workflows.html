Workflows

A workflow is a saved graph of nodes that runs on the Temporal-backed workflow engine. It can query data, run sandboxed JavaScript, branch, loop, wait, call another workflow, collect human input, and require an approval decision.

Core concepts​

ConceptMeaning
Workflow definitiontblWorkflows plus tblWorkflowNodes and tblWorkflowEdge. Node positions and configuration live in nodeConfig.
InstanceOne run, stored in tblWorkflowInstances; logs are in tblWorkflowInstanceLogs. The Temporal workflow ID is the instance ID.
ctxThe run's mutable data context. Inputs are ctx.input; node outputs are stored under each node's outputVariable.
Template expression{{ctx.path}} in node configuration. Resolved at node execution time in safe-path mode; JavaScript expressions are only allowed in the condition's JS-expression operator and in JavaScript nodes.
Output variableA JavaScript identifier (letters/digits/underscore, starting with a letter/underscore) used as the context key for a node result.
Edge handleThe named output port on a node (success, error, a branch id, approved, loop, completed, …). Routing follows the handle.
Execution policyTimeout/retry defaults resolved as node data → workflow options (nodeDefaults or workflow defaults) → platform default.
Test runA persisted isTest instance that executes the unsaved graph through Temporal. It is cleaned up by the test-stop endpoint.
Human-in-the-loopdataCollection and approval suspend the run until a user submits a form/decision or the request expires.

Supported node types​

The executable runtime supports 13 node types. connectorPull and connectorPush appear in the frontend constants but have no runtime handler and are not valid in a saved workflow.

NodePurposeOutput handles
startMandatory single entry point.output
dataQueryExecute a saved data query.success, error
javascriptRun sandboxed JS and return a value.success, error
conditionOrdered structured branches; first match wins.branch id, default, error
switchRoute on one value across named cases.case id, default, error
loopIterate an array; execute the body per item.loop, completed, error
delayDurable sleep (fixed/dynamic/until).output, error
dataCollectionSuspend for a human form.output, error (timeout fails unless a timeoutHandle is configured)
approvalApprove/reject decision with comment.approved, rejected, expired, error
subWorkflowRun a saved child workflow synchronously.success, error
fanoutTake every named branch.branch id, error
joinBarrier + merge of upstream outputs.output, error
endTerminate with success/failure/cancelled status.none
note

condition.evaluationMode: "all_matches" is accepted by the editor schema but the runtime implements first-match only. Use first_match (the default) or build separate branches.

Node configuration reference​

Every non-terminal node supports:

FieldDescription
title / descriptionCanvas labels/documentation. Node descriptions are persisted; a workflow-level description is accepted by the API but is not persisted by the current service.
errorHandlingfail_workflow, continue, retry_then_continue, retry_then_fail; the validator also accepts skip_item (loop bodies) and continue_default (condition).
isDisabledIf true, the node is skipped and execution follows a default success/output path.

Start​

The start node has only title/description. Input parameters are defined at workflow level in workflowOptions.inputDefinitions:

Parameter fieldTypeNotes
keyStringContext key under ctx.input.
typestring, number, boolean, object, arrayCoerced at trigger time.
requiredBooleanMissing required inputs fail the run.
defaultValueMatching typeApplied when the input is missing.

Data Query​

FieldDescription
dataQueryIDUUID of a saved query in the same tenant. Required.
inputValuesMap of query argument key → template/literal, e.g. {"status":"{{ctx.input.status}}"}.
outputVariableDefault queryResult.
timeoutSeconds1–3600. Effective default is 120 s for this node type when the field is absent.
retryLimit0–10 retries after the first attempt.
retryDelaySeconds0–300 seconds between attempts. Delay is fixed, not exponential.

The result is the connector's result (for SQL, usually an array of rows). Access it with {{ctx.queryResult}} or {{ctx.queryResult[0].field}}.

JavaScript​

FieldDescription
codeCode must use return to produce a value.
outputVariableDefault jsResult.
timeoutSeconds1–300; default 30 s.
retryLimit / retryDelaySecondsSame semantics as data query.

The sandbox exposes ctx and a limited set of globals (JSON, Math, Date, Array/Object/String/Number/Boolean, parseInt, parseFloat). It has no network, filesystem, require, or npm modules.

const order = ctx.order[0];
return {
  requiresApproval: Number(order.total) > 5000,
  customerEmail: order.email
};

Condition​

FieldDescription
branches[]Ordered branch objects. Each has id (the outgoing handle), name, conditionLogic (AND/OR), and conditions[].
conditions[].leftValueTemplate or value, e.g. {{ctx.order[0].total}}.
conditions[].operatorequals, not_equals, contains, not_contains, starts_with, ends_with, greater_than, less_than, greater_or_equal, less_or_equal, is_empty, is_not_empty, matches_regex, expression.
conditions[].rightValueComparison value/template; not used by unary operators.
evaluationModeUse first_match; all_matches is not honored.

The first matching branch wins. If none match, the default handle is taken. The JS-expression operator uses raw ctx (no {{ }}), for example ctx.score > 80 && ctx.tier === 'gold'.

Switch​

FieldDescription
switchValueTemplate or literal, e.g. {{ctx.input.kind}}.
cases[]{ id, label, operator, matchValue }; id is the outgoing handle. Operators: equals, not_equals, contains, greater_than, less_than, expression.
default handleUsed when no case matches.

Loop​

FieldDescription
sourceVariableTemplate resolving to an array, e.g. {{ctx.customers}}. Required.
itemVariable / indexVariableContext keys for the current item/index; defaults item/index.
outputVariableArray of per-iteration results; default loopResults.
maxIterations1–100,000; default 1000. A larger source fails the node.
delayBetweenItemsMilliseconds (0–60,000) between iterations.
errorHandlingfail_workflow, continue, or skip_item.

Execution:

  • The engine copies the current context per iteration and sets ctx.<itemVariable> / ctx.<indexVariable> (also item/index aliases).
  • It walks the body from the loop handle. A back-edge to the Loop node is accepted as the iteration boundary; the body can also end without one.
  • The last node's output per iteration is appended to loopResults. If that output has one public key, its value is collected; if several, the object is collected.
  • After all items, execution follows completed.

Delay​

FieldDescription
delayTypefixed, dynamic, until.
delayMinutes / delaySeconds / delayMsFixed delay components: 0–1440 / 0–59 / 0–999, additive.
delayVariableDynamic delay in milliseconds, resolved from context.
untilTimeISO timestamp or template; past times proceed immediately.

Maximum delay is 24 hours. Delays are durable Temporal sleeps, not held threads.

Data Collection​

FieldDescription
title / descriptionModal heading and instructions.
collectionTypeform.
formSchemaRequired JSON Schema (type: object) used by Ajv to validate the submission.
formUischemaOptional JSON Forms layout.
fieldsBuilder convenience list; the runtime contract is formSchema.
outputVariableDefault collectedData.
expiryMinutes0–10080; 0 means no deadline.

On submit, the backend validates submittedData against formSchema, stores it, and signals the workflow. On expiry, the run fails unless a timeoutHandle is stored in node data (not exposed by the standard editor).

Approval​

FieldDescription
title / descriptionModal text; supports templates.
approversDisplay-only hint. It does not restrict who can decide.
requireCommentAdds comment to the required schema fields.
approveLabel / rejectLabel / cancelLabelButton labels.
expiryMinutes0–10080; 0 means no deadline. UI default 60.
onTimeoutexpired (default; follow the expired handle) or fail (fail the run).
outputVariableDefault approval; stores { approved, decision, comment }.

Submitting stores:

{
  "approved": true,
  "decision": "approve",
  "comment": "Within budget"
}

Expiry routes with { "approved": false, "decision": "expired", "expired": true, "comment": "" }. Cancel closes the modal without a decision and leaves the run paused.

Sub-Workflow​

FieldDescription
childWorkflowIDSaved workflow in the same tenant; self-reference is rejected.
inputMappingChild input key → template resolved against the parent context.
outputVariableDefault subResult; receives the child's End outputs.
mergeOutputsSpread the child's public top-level outputs into the parent context (child wins; input is not overwritten).
maxDepth1–10; default 5.
timeoutSecondsCaps the total child wait; 1–3600.
retryLimit / retryDelaySecondsSame as other nodes.

The child sees only the mapped inputs as ctx.input; it never sees the parent context. The parent also receives childInstanceID and childStatus. A child that ends with FAILED/CANCELLED is treated as a failed node. Use inputMapping; inputValues on a sub-workflow node is ignored.

Fan-out and Join​

Fan-out fires every branch id unconditionally. The runtime executes branches sequentially in deterministic order (path parallelism, not threads). Join waits according to joinMode (all default or any), then merges the listed bare context keys into outputVariable (default joined).

Join fieldDescription
sourceVariables["aResult","bResult"] — bare names, not {{ctx.*}}.
requireAllIf true (default), a missing variable fails the node instead of merging null.
joinModeall or any. Untaken exclusive paths are marked inactive so an all join is not permanently blocked by a branch that cannot run.

End​

FieldDescription
statussuccess, failure, or cancelled. A failure/cancelled End marks the workflow run failed/cancelled.
outputParameters[]{ name, sourceVariable, description? }. Source is a template; outputs become the instance's workflowOutput.

Every workflow needs at least one End node; multiple End nodes are normal for terminal branches.

Context and templates​

  • ctx.input holds trigger inputs.
  • Each node writes its output under outputVariable; later writes to the same key win.
  • ctx.item / ctx.index exist during loop body execution.
  • Internal keys starting with __ are not exposed in run-status context.
  • Template resolution is safe-path: {{ctx.a.b[0].c}}. No function calls or operators. Use a JavaScript node for computation.
  • Missing paths resolve to undefined (rendered as empty/null depending on the field); they do not throw by themselves.

Build a workflow in the UI​

  1. Open Workflows and choose Add workflow.
  2. Enter a title. The workflow is saved with an empty graph.
  3. In the editor, drag nodes from the palette onto the canvas.
  4. Connect handles: Start output, Data Query success/error, Condition branch ids, Approval decision handles, Loop loop/completed, etc.
  5. Open a node to edit its JSON-Forms configuration; set output variables and advanced policy.
  6. Define Input Parameters in the left panel (workflowOptions.inputDefinitions).
  7. Use Test Run with sample inputs; inspect the Console and Context panels.
  8. Save, then run from the list or execute through the API/widget/listener.

A graph is validated at save/test time:

  • exactly one Start node and at least one End node;
  • unique node IDs (UUIDs in the database), no self-loops, no invalid edge endpoints;
  • valid branch/case handles for condition/switch/fan-out;
  • referenced queries and child workflows belong to the same tenant;
  • the executable check (test/start) additionally rejects cycles that do not contain a Loop node, invalid/unsupported handles, and nodes not reachable from Start.

Execution policy​

tblWorkflows.workflowOptions supports:

KeyMeaning
inputDefinitionsWorkflow input schema.
workflowRunTimeoutTemporal run timeout; default 7 days.
workflowTaskTimeoutTemporal task timeout; default 30 seconds.
humanInLoopTimeoutDefault human wait; default 24 hours (used when a node has no expiryMinutes/timeout).
defaultNodeTimeoutSeconds1–3600; default 120.
defaultRetryLimit0–10; default 0.
defaultRetryDelaySeconds0–300; default 5.
nodeDefaultsPer-node-type overrides, e.g. { "javascript": { "timeoutSeconds": 60 } }.

Precedence: node data → nodeDefaults[type] → workflow default → platform default.

warning

The node editor's initial values are not the platform defaults. For example, a newly added Data Query node starts with timeoutSeconds: 300, while the platform default for a Data Query whose timeout field is absent is 120 s. Set the value explicitly when it matters.

Retries and error handling​

errorHandlingBehaviour
fail_workflowStop the run on failure.
continueFollow the error handle; the node output stores success: false and the error.
retry_then_continueRetry up to retryLimit, then follow error.
retry_then_failRetry, then fail the run.
skip_itemLoop bodies only: skip the current iteration.
continue_defaultCondition only: follow default when evaluation fails.

Retry delay is fixed (retryDelaySeconds) between attempts. Deterministic user-code errors (syntax errors, undefined identifiers, non-retryable application failures) are not retried. retryLimit counts retries after the first attempt.

Run status and monitoring​

Instance statuses: PENDING, RUNNING, COMPLETED, FAILED, CANCELLED. A suspended human node is RUNNING at instance level with a SUSPENDED node log/request.

SignalWhere
Node progressSocket.IO room per instance; the editor Console shows RUNNING/SUCCESS/FAILED/SKIPPED/SUSPENDED.
ContextGET /workflows/instances/:instanceID returns assembled contextData (internal __ keys stripped).
Pending formspendingDataCollectionRequests in run status; the modal also arrives via workflow_data_collection_request on the instance room.
HistoryGET /workflows/instances?workflowID=&status=&isTest=&parentInstanceID=
Sub-workflow linkageparentInstanceID / parentNodeID on the child instance.

Human-in-the-loop is not an assignment/notification system: approvers is a label. A user only sees the modal if they open/subscribe to the run and has workflow:execute on the parent workflow when submitting. Build an external notification step if reviewers must be alerted.

Limitations and failure modes​

FailureCause / handling
No start node / requires at least one end nodeAdd the missing terminal structure.
No handler found for node typeUse a supported type; connectorPull/connectorPush are not executable.
Invalid ... output handleAn edge uses a handle the node does not expose. Check branch/case ids and approval handles.
Graph deadlockA Join waits for an upstream path that can never become active. Use joinMode: "any", connect all branches, or remove the join.
Graph cycle must use an explicit loop boundaryAdd a Loop node or remove the back-edge.
Loop has N items > maxIterationsRaise maxIterations (max 100,000) or pre-filter the source.
Max depth exceededSub-workflow recursion exceeds maxDepth (1–10).
Approval expired / data collection timeoutExpiry reached. Approval routes to expired unless onTimeout: "fail"; data collection fails unless a custom timeoutHandle exists.
Workflow is no longer running on form submitThe run was cancelled/terminated, or another submission won the race.
Temporal not running at ...Start Temporal (local compose) and configure TEMPORAL_ADDRESS; workflows cannot execute without it.
Run history disappearsDeleting a workflow deletes its instances/logs. Test-instance stop also deletes that instance.
Start succeeds but nothing happensCheck the Temporal worker is running and polling TEMPORAL_TASK_QUEUE; start returns an instance ID before execution completes.
Sub-workflow input missingUse inputMapping (not inputValues); the child only sees mapped inputs.

Security notes​

  • workflow:execute is the gate for starting a workflow and for submitting its human forms. approvers is not an authorization list; any user with execute can decide.
  • Referenced queries and child workflows are checked at save and execute time for tenant ownership and execute permission.
  • The JavaScript node runs in an isolate with no network/filesystem. Treat all ctx values as untrusted and validate before using them in downstream queries.
  • Listener/cron-triggered workflows run with a system context and skip per-user query authorization inside the workflow; protect who can edit listeners/cron jobs.
  • Workflow context and logs may contain PII. Run history is tenant-scoped but not field-encrypted; avoid storing secrets in ctx.

Troubleshooting​

  1. Validate the graph by saving or starting a test run; handle errors point at the node/edge index.
  2. Open the run and inspect node logs/context; a failed node usually has the underlying connector error.
  3. Check output variable names — duplicate or invalid identifiers overwrite/route unexpectedly.
  4. Check branch handles — edge sourceHandle must equal the branch/case id exactly.
  5. Check input mappings — query/workflow inputs are keyed by the target's inputDefinitions.
  6. Check Temporal — client connection, worker process, namespace, task queue, and run timeout.
  7. Check policy — node timeout may be lower than the query's runtime; retries multiply total duration.
