Introduction

Jet Admin is a self-hosted platform for connecting to operational data, querying and listening to it, automating work with workflows, and composing the results into widgets, app pages, and routed applications. Everything runs inside an isolated tenant and is authorized with tenant-scoped roles and permissions.

It is closest to the "internal tools" category — part data console, part automation engine, part low-code app builder — rather than a pure BI tool. The repository describes the product as an open-source analytics platform and internal tools builder; the codebase shows the same shape: a PostgreSQL-backed system store, a plugin-style connector layer, a DAG workflow engine, Socket.IO real-time delivery, a canvas page builder, and a release layer for multi-page applications.

Current version

The root package.json identifies this checkout as 2.1.0-preview.1. Treat the platform as preview-grade for externally facing or business-critical applications, and read Honest scope before committing to it.

Jet Admin assumes you are comfortable with SQL, HTTP APIs, JSON, and environment variables. The UI removes a lot of application code, not the need to understand the data and failure modes underneath it.

What it is — and what it is not​

Jet Admin isJet Admin is not
A self-hosted internal-tools and operations platformA general-purpose SaaS BI suite with a semantic modeling layer
A tenant-scoped environment with Casbin RBAC, API keys, and audit logsA replacement for your identity provider (it uses Firebase for human sign-in)
A query and action layer over databases, SaaS APIs, queues, and webhooksA database, a CDC product, or a managed integration platform
A visual workflow engine with human approval and data-collection nodesA general-purpose durable-execution platform comparable to raw Temporal
A canvas app builder with reusable widgets and page versionsA native mobile app builder or a public anonymous web-app host
A release layer that pins page and dependency versions per applicationA fully mature application platform with row-level security and zero-downtime migrations

Mental model​

The platform is easiest to understand as a build order. A tenant owns every resource. Inside it, connections feed queries and listeners. Those feed workflows, widgets, app pages, and applications. Administration wraps all of it.

A useful shorthand:

Tenant → Connection → Query or Listener → Workflow or Widget → Page → Application → Release.

Each arrow is a real reference in the database, not just a conceptual grouping. That is why export/import bundles can walk dependencies, and why an application release can pin exact page versions.

How a request moves​

The runtime is a modular monolith with two specialist services. In the Docker reference stack, the browser talks to nginx, nginx proxies to the backend, and the backend talks to PostgreSQL, Redis, Temporal, and external systems.

Relevant operational facts:

  • Human requests use a Firebase ID token; automation uses an API key.
  • Every tenant route is gated by membership and Casbin policy evaluation.
  • Secrets are encrypted at rest with VAULT_ENCRYPTION_KEY (AES-256-GCM).
  • Listener ingress is open by design at /webhooks/...; the path suffix is the secret.
  • Socket.IO handles live listener delivery and workflow progress.
  • The docs deployment is separate from the application deployment; see Deployment.

What makes Jet Admin different​

  1. Query-first, not spreadsheet-first. The primary abstraction is a saved query against a real data source, with explicit input definitions and tenant-scoped execution. Widgets and pages bind to those queries rather than owning data.

  2. Event ingress is part of the product. Listeners support databases (PostgreSQL LISTEN, MongoDB change streams, Firestore), queues and brokers (Kafka, RabbitMQ, NATS, MQTT, Redis), HTTP ingress (webhook, SSE, WebSocket), GraphQL subscriptions, and syslog. The listener pipeline can transform events and trigger queries, workflows, or app-page pushes.

  3. Tenant isolation and delegated execution are first-class. Assets are scoped to a tenant, API keys are distinct authorization subjects, and workflows/pages can execute inner resources through the caller's identity plus an origin reference.

  4. Applications add a release boundary. App pages can be composed into routed applications; publishing captures immutable page versions and deploys a thin release to the production environment. Rollback moves the production pointer.

  5. Extension is package-driven. Datasource connectors, widget renderers, workflow nodes, and shared UI live in workspace packages, so adding a connector or widget does not require editing a central switchboard.

  6. Automation is exposed to agents. The in-app Jet Agent uses an OpenRouter-compatible model, and the MCP server exposes a large tool catalog for external MCP clients.

None of these is unique in isolation. The combination — self-hosted, tenant-scoped, query/listener/workflow/app in one system — is the reason to consider Jet Admin.

A sensible learning order​

  1. Tenant + IAM. Create a workspace, understand Admin vs Member, and create a scoped API key.
  2. Data source + query. Connect a non-production database and prove a read query works before building UI.
  3. Widget + page. Bind the query to a table or chart and confirm the page runtime executes it on load.
  4. Workflow. Add one multi-step action with an explicit error path.
  5. Listener. Only after Redis and the listener proxy are running, add event ingress.
  6. Application. Compose pages into routes only when the pages are stable enough to version.
  7. Operations. Add folders, audit review, exports, and a deployment/rollback process.

Honest scope​

Read this before a production commitment

Jet Admin is ambitious and broad, but it is not a finished enterprise product. The following are deliberate, evidence-based caveats — not marketing language.

  • Preview release. The repository version is 2.1.0-preview.1, and the README itself says the project "has a few bugs and rough edges." Plan a pilot, not a big-bang migration.
  • Applications are a foundation, not a proven runtime. The project's own status document says composition, versions, releases, routing, and consumer policy are implemented, but "this is not a claim of production readiness," and live Temporal/Redis/listener-proxy verification remains blocked.
  • No built-in SSO/SCIM. Human authentication is Firebase-based (email/password, Google sign-in, or whatever the Firebase project is configured for). There is no SAML/OIDC/SCIM implementation in the repository.
  • No application-level rate limiting or Helmet. The security documentation explicitly lists these as gaps; enforce limits and headers at your edge proxy.
  • No row-level security layer. Tenant isolation and asset permissions are enforced in application code/Casbin. Authorization does not filter individual rows returned by a query. If different users must see different rows, encode that in query arguments and the underlying database permissions.
  • No exactly-once guarantee. Workflows and listener actions can retry, but the platform does not promise exactly-once side effects or duplicate-submit prevention. Make mutations idempotent where it matters.
  • Connector depth varies. The registry has many connectors; not every connector has the same maturity, pagination support, or test coverage. Validate the specific connector and operations you need.
  • No public/anonymous consumer identities. Application runtime is for authenticated tenant members. Application-level consumer policy can restrict routes and data-source aliases, but it does not add external identities.
  • Licensing needs a check. The README says MIT, but this checkout does not contain a root LICENSE file. Confirm the current license with the maintainers before redistributing or embedding the project.

Jet Admin may not be the right choice if…​

  • You need a governed BI semantic layer, scheduled dashboard subscriptions, and a large analyst community. Metabase or Superset will be a better fit.
  • You need a mature, highly polished internal app builder with a large connector marketplace and enterprise SSO today. Retool, Appsmith, or ToolJet are safer short-term choices.
  • You need durable, code-first orchestration with strong replay semantics for payments or supply-chain flows. Use Temporal directly, or Windmill for script-centric workflows.
  • You need a headless CMS or content API. Use Directus.
  • You need public customer-facing apps with anonymous users and row-level tenant isolation at the database level. Jet Admin's current application/consumer model is not that product yet.

Glossary​

TermMeaning in Jet Admin
TenantIsolated workspace; the authorization domain for every asset.
DatasourceA stored connection configuration plus encrypted credentials.
Data queryA saved query definition with typed input definitions.
ListenerA long-lived subscription or webhook ingress bound to one datasource.
Pipeline actionA listener step: transform, trigger query, trigger workflow, save to buffer, or push to app page.
WorkflowA DAG of nodes with a shared execution context (ctx).
WidgetA reusable visual component with a config and event handlers.
App pageA canvas layout plus data-source aliases, variables, and widget placements.
ApplicationA routed composition of pages with a shell, state, policy, releases, and environments.
ReleaseAn immutable application snapshot referencing exact page/dependency versions.
Environment bindingA mapping from datasource IDs captured by a release to live tenant datasources.
BundleA sanitized JSON export of a resource and its dependency closure.
MCPModel Context Protocol; the bridge that exposes Jet Admin tools to AI clients.
